# 대본

## Git 교육 시작

이제 13기 첫 CS 교육을 시작하겠습니다.

---

교육 목차는 다음과 같습니다.

Git이 무엇인지부터, 기본적인 이해부터 알아볼 거구요,

Git의 핵심 구조가 어떻게 이루어져있는지, 어떤 흐름으로 사용하는지를 배우며,

마지막으로 협업 시 필요한 기본 명령어를 배우고 마무리하려고 합니다.

---

우선 Git이란 무엇일까요?

정의부터 보고 가겠습니다.

‘빠르고 효율적으로 코드 변경 이력을 관리하며, 안전한 협업을 가능하게 하는 무료 오픈 소스 분산 버전 관리 시스템’이라고 나와있죠? 

Distributed Version Control System, 축약형으로는 Distributed VCS라고도 합니다.

Git에 대해 정확하게 이해하기 위해서는 ‘버전 관리’와 ‘분산’이라는 단어를 먼저 이해해야하는데요.

---

우선 버전이라는 건, 소프트웨어나 문서의 특정 시점의 상태를 의미하죠?

ver1, ver2,.. 이런 식으로요 버전을 기록하면서 기능 개발이나 실험등을 독립적으로 진행할 수 있는데요.

---

그렇다면 ‘버전 관리’의 의미는 다음과 같습니다.

‘소스 코드나 문서 등의 변경 사항을 추적하고 기록하는 시스템.’입니다.

즉, 파일의 모든 **변경 내역**을 기록하여 파일의 현재 상태 뿐만 아니라 과거 상태 관리가 가능하며, 쉽게 이전 상태로 되돌아갈 수도 있도록 하여 버전을 쉽게 관리할 수 있는 것이죠.

---

그렇다면 Git이 어떻게 효과적으로 버전 관리를 도와주는 걸까요?

우선 버전 관리를 크게 두 가지 관점으로 나눠 볼 수 있는데요.

시간과 차원의 관점에서 살펴보겠습니다.

---

먼저 시간의 관점인데요.

우리가 작업을 하다 보면, 시간에 흐름에 따라 이런 식으로 버전1, 버전2, 3, 4.. 이렇게 점을 찍어가듯이 차례대로 발전해나가죠.

이때 우리는 각 시점의 파일 상태를 알고 있고, 필요하면 언제든지 V2나 V3로 돌아갈 수 있습니다.

이게 바로 **시간 관점으로서의 버전 관리**입니다.

프로젝트의 모든 순간을 기록해두는 것이죠.

---

다들 이런 경험 한 번쯤 해보셨을 것 같은데요.

- 기획서_v1.zip
- 기획서_v2.zip
- 기획서_최종.zip
- 기획서_진짜최종.zip

이렇게 파일을 계속 복사해서 이름만 바꿔 저장하는 방식의 문제점은 뭘까요?

1. 어떤 게 최신인지 헷갈립니다.
2. 중간 버전을 찾기 어렵습니다.
3. 누가 무엇을 바꿨는지 알 수 없습니다.

즉, 체계적인 ‘시간 관리’가 되지 않습니다.

---

만약, 이 찐막 버전 파일에서 큰 실수를 했다고 가정해볼게요.

파일을 덮어써버렸거나, 중요한 내용을 삭제해버리는 상황이 발생할 수 있잖아요?

---

이때, 이전 버전이 체계적으로 관리되지 않았다면, 누가 수정했는지, 해당 버전이 직전 버전에서 어떤 부분이 변경됐었는지 등 헷갈리기가 쉬워 체계적인 관리가 어렵습니다.

---

하지만 Git을 사용하면 V4가 잘못되었을 때, 얼마든지 V3로 정확히 되돌릴 수 있습니다.

파일을 복사해둔 게 아니라, **변경 이력 자체를 저장하고 관리하기 때문입니다.**

이게 Git이 말하는 ‘버전 관리’입니다.

단순 저장이 아니라, 시간을 관리하는 시스템입니다.

프로젝트의 모든 순간이 기록되고, 우리는 언제든 과거로 이동할 수 있습니다.

---

하지만 이런 시간 관리만으로서는 부족하고, 차원 관점에서도 관리가 이루어져야 하는데요.

한 프로젝트를 여러 사람들과 협업할 때, 누군가는 A기능을 맡고 누군가는 B기능을 맡아 작업을 하죠?

이때 서로 영향을 주지 않고 각자 다른 공간에서 작업할 수 있어야 하는데요.

---

만약 git과 같은 버전 관리 시스템이 없다고 가정해볼게요. 

각자 이렇게 개별적으로 작업을 마쳤을 때, 

---

이걸 어떻게 합칠 수가 있을까요? A가 B에게 자신의 파일을 보내주고 B가 알아서 그 위에 또 덮어써야 할까요? 그럼 일을 두 번 하게 되는 셈이니 매우 비효율적일 것입니다.

---

Git에서는 이렇게 각자 기능을 분담해 개발할 수 있는 독립적인 공간인 브랜치를 활용해, 효율적인 협업이 가능하도록 도와줍니다.

---

브랜치가 영어로 ‘가지’를 의미하는 단어잖아요.

나무가 자라면서 여러 갈래로 가지를 뻗어나가듯이, Git에서도 하나의 프로젝트가 여러 갈래로 나뉘어 동시에 작업될 수 있습니다.

이 브랜치 덕분에 다양한 작업을 독립적으로 진행할 수 있고, 각각의 작업이 프로젝트 전체에 영향을 주지 않도록 관리할 수 있습니다.

---

즉, Git의 기본 기능은 **시간** 흐름에 따라 버전을 기록하는 것이고, 브랜치 기능을 통해 그 흐름을 여러 갈래로 나누는 것이라고 할 수 있겠습니다.

---

제가 아까 처음에 git이 분산 버전 관리 시스템이라고 했죠?

지금까지 버전 관리가 어떻게 이루어지는지 알아보았으니, 그럼 여기서 분산이라는 건 어떤 의미일까요?

모든 개발자가 **코드와 변경이력이 모두 있는 전체 저장소를 각자 로컬에 복제해서 작업하는 구조**를 의미합니다.

즉, 중앙 서버에서만 의존적으로 코드를 관리하지 않는 것이 아니라, 각자 하나씩 완전한 저장소를 가지고 있는 것이죠.

그렇기 때문에 서버에 문제가 생겨도 각자의 로컬 저장소에 버전이 보관되어 있으므로 복구가 쉽게 가능하고, 

여러 개발자가 협업 시에 동일한 코드를 가지고 병렬적으로 작업이 가능하며, 각자의 작업을 병합하는 과정이 유연합니다.

---

그럼 Git과 GitHub는 무엇이 다를까요?

Git은 앞서 계속 말했듯 VCS, 즉 ‘버전 관리를 도와주는 시스템’이고, GitHub는 Git 저장소를 온라인에 올려 협업할 수 있게 해주는 웹 서비스 플랫폼입니다.입니다.

원격 저장소라고도 부르는데요, github는 pull request, Issue, Code Review와 같은 다양한 협업 기능을 제공합니다. 그 외에도 Actions와 같은 CI/CD 기능도 제공하죠. 

그리고 웹에서 바로 코드를 확인하는 것도 가능합니다.

---

이제 Git의 내부 구조에 대해서 조금 더 자세히 볼 건데요,

Git에서 각 파일은 4가지 상태로 관리됩니다.

Untracked: 말 그대로, 아직 Git이 관리 및 추적하지 않는 파일입니다. 보통 새로 생성한 파일은 생성되자마자 git 저장소에 자동 저장되는 게 아니라, untracked 상태가 됩니다.

Modified: 수정은 되었으나, 아직 커밋으로 저장되지 않은 파일은 modified 상태입니다.

Staged: 커밋할 파일로 선택된 상태로서, 스테이징된 파일이라고 할 수 있습니다.

Committed: 커밋으로 저장이 완료된 상태입니다.

---

이에 따라 git은 다음과 같은 공간에서 각 파일들의 상태를 관리하는 데요.

1. working directory: 내 컴퓨터에서 실제로 파일을 만들고, 수정하는 공간입니다. 새로 만든 파일(untracked)도 있고, 기존 내용을 수정한 변경 파일(modified)도 있을 수 있습니다.
2. staging area: 커밋하기 이전에, 수정된 파일을 저장하는 장소라고 할 수 있습니다. 
3. local repository: 커밋된 파일들이 보관되는 저장소입니다.

여기까지는 내 노트북에 한정해서 자유롭게 공간을 넘나들 수 있었다면,

1. remote repository: 원격 저장소, 즉 모든 작업자의 push된 코드를 모아두는 저장소입니다.

---

마지막으로, 협업 시에 필수로 사용하는 명령어들의 역할과 기본 플로우에 대해 알아보고 마칠게요.

우선 git clone: 

원격 저장소인 github에 있는 프로젝트를 내 컴퓨터에 그대로 내려받아 가져올 때 사용하는 명령어

git add: 

수정한 파일을 staging area에 올리는 명령어

→ 다음 커밋에 포함될 파일을 선택한다.

 git commit:

staging area에 있는 파일들을 하나의 버전(커밋)으로 저장

→ 변경 이력이 기록된다.

git push: 

로컬 저장소의 커밋을 원격 저장소(GitHub)로 업로드하는 명령어

git pull:

원격 저장소의 최신 변경 내용 → 로컬에 반영

git merge:

다른 브랜치의 변경 내용을 현재 브랜치에 합치는 명령어

---

이러한 명령어들을 사용하게 되는 기본 플로우는 이렇습니다.

깃허브에 있는 레포지토리를 clone 해오고, 가장 최신 코드를 pull 하며, 작업을 진행합니다. 

그리고 이 작업한 파일들을 add 명령어로 staging area에 올리고, 

commit 명령어를 통해 staging area에 있던 파일들을 하나의 버전, 즉 커밋으로 저장합니다.

그리고 다른 팀원들과 공유할 수 있도록 push 명령어를 통해 원격 저장소에 업로드합니다.

이때, push를 하기 전에 꼭 pull, 즉 원격 저장소의 최신 변경 내용을 로컬에 반영하도록 하는 작업이 중요한데요.

파일을 최신 버전으로 동기화하고, 다른 팀원의 작업 내용과의 충돌(conflict)을 방지하기 위함입니다.

---

지금까지의 내용을 정리하면,

git은 분산 버전 관리 시스템이며,

시간 흐름에 따라 버전을 기록하고, 브랜치 기능을 통해 그 흐름을 여러 갈래로 나누어 기록 뿐만 아니라, 유연한 병합까지 가능합니다.

이로써 안전한 협업을 가능하도록 해줍니다.
