### 슬라이드 10: 컴퓨터 내 저장장치의 계층 구조

컴퓨터 내부의 저장장치들은 이렇게 계층 구조를 이루고 있는데요.

위에서부터 레지스터, 캐시 메모리, RAM 메모리, SSD, 하드디스크와 같은 보조기억장치 순입니다.

레지스터와 캐시 메모리는 CPU 내부, 혹은 가까이에 있는 아주 빠른 임시 공간인데요.

위로 올라갈수록 CPU 코어와 가깝기 때문에 속도는 빠르고, 용량은 작고, 가격은 비쌉니다. 반대로 아래로 내려갈수록 속도는 느리고, 용량은 크고, 가격은 저렴해져요.

가장 앞단에 있는 레지스터에도 임시 저장장치가 있지만, 소량의 당장 사용할 데이터만 담아두고 처리하고, 캐시 메모리는 메모리나 보조기억장치에 비해 저장 공간이 작고 가격은 비싸지만, 빠른 속도를 제공합니다.

### 슬라이드 11: 캐시(Cache)란 무엇일까? — 정의

이제 캐시의 정의를 제대로 내려보자면,

캐시란, **자주 사용하는 데이터나 값을 미리 복사해 놓는 임시 저장소**입니다.

딸기 예시에서의 냉장고와 같은 역할이에요.

조금 더 공식적으로 말하면, 소프트웨어 또는 하드웨어의 효율성을 높이기 위해 사용되는 여러 유형의 임시 메모리 저장소를 지칭합니다.

요약하면, 원본 데이터를 매번 가져오기엔 시간이 걸리니까, 자주 쓰는 건 빠른 곳에 미리 복사해두는 거예요.

### 슬라이드 12: '캐시로 처리한다'는 것의 의미

그래서 '캐시로 처리한다'는 말은 실제로 이런 의미입니다.

결과를 저장해두고, 똑같은 요청이 오면 그 요청에 대해서 DB 또는 API를 참조하지 않고 캐시를 참조하여 요청을 처리한다.

예를 들어, 여러분이 유튜브에서 같은 영상 썸네일을 계속 보게 될 때, 매번 서버에서 새로 내려받는 게 아니라 이미 저장해둔 걸 바로 보여주는 거예요. 이렇게 하면 속도도 빠르고, 서버 부담도 줄어들 수 있습니다.

### 슬라이드 13: 파레토의 법칙

그런데 여기서 한 가지 질문이 생길 수가 있는데요. "모든 데이터를 캐시에 넣어두면 안 되나요?" 라고요.

아까 봤듯이 캐시는 빠른 만큼 용량이 작아서, 다 넣을 수가 없습니다.

그렇다면 어떤 데이터를 캐시에 넣어야 할까요? 여기서 **파레토의 법칙**이라는 이론이 등장하는데요.

80%의 결과는 20%의 원인으로 인해 발생한다는 법칙이에요.

예를 들어, 어떤 가게의 80% 매출이 20%의 단골들에게서 나온다는 식이죠.

캐시에도 이 원리가 적용되어서, 핵심 데이터 20%가 전체 요청의 80%를 차지하므로, 캐시에 넣어두면 대부분의 요청을 빠르게 처리할 수 있다는 것입니다.

### 슬라이드 15: 지역성의 원리 — 정의

지역성이란, 기억장치 내의 정보를 균일하게 접근하는 것이 아닌, 어느 한 순간에 특정 부분을 집중적으로 참조하는 특성을 말합니다.

쉽게 말해서, 우리가 컴퓨터로 무언가를 할 때, 데이터에 골고루 접근하는 게 아니라 특정 데이터에 집중적으로 접근한다는 것인데요.

예를 들어, 여러분이 유튜브를 볼 때 메인 피드, 구독 피드, 최근 본 영상 같은 특정 데이터에 반복해서 접근하지, 유튜브의 모든 영상 데이터를 균등하게 보지는 않잖아요.

---

### 슬라이드 16: 지역성의 원리 — 시간 지역성 & 공간 지역성

이러한 지역성에는 두 가지 종류가 있어요.

첫 번째, **시간 지역성입니다**. 최근에 접근했던 메모리 공간에 다시 접근하려는 경향입니다.

예를 들어 for문의 조건 변수 i를 떠올려 보면, 반복문을 돌 때마다 i를 계속 읽고 쓰잖아요. 최근에 쓴 걸 또 쓰는 것입니다.

두 번째는, **공간 지역성인데요**. 접근한 메모리 공간의 근처에 접근하려는 경향입니다.

예를 들어 array[0]에 접근하면, 곧이어 array[1], array[2]... 이렇게 근처 데이터도 접근하게 되는 것입니다.

---

### 슬라이드 17: 지역성의 원리 — 캐시와의 연결

이 시간 지역성과 공간 지역성, 이 두 가지 성질 덕분에 

'자주 쓰는 데이터를 미리 빠른 곳에 가져다 놓는다'는 캐시 전략이 실제로 효과를 발휘할 수 있어요.

"어차피 곧 또 쓸 거잖아?" 라는 예측을 할 수 있기 때문에, 미리 캐시에 올려두는 전략이 실제로 들어맞는 거예요.

여기까지 캐시가 무엇인지, 그리고 왜 필요한지 이해하기 어려운 부분 없으시죠?

---

### 슬라이드 18: 캐시의 동작 원리 — 플로우차트

이제 캐시의 동작 원리를 좀 더 자세하게 보겠습니다.

먼저 데이터 요청이 들어옵니다.

그러면 캐시를 먼저 확인해요.

만약 캐시에 데이터가 있다면? 바로 빠른 속도로 반환하게 되면서, 응답이 완료됩니다 이게 바로 **Cache Hit**입니다.

만약 캐시에 데이터가 없다면? 원본 저장소인 DB나 서버로 가서 조회해요. 가져온 데이터를 캐시에 저장해두고, 그리고 반환합니다. 이게 **Cache Miss**입니다.

Cache Miss가 발생해도 한 번 저장해두면, 다음 요청부터는 Cache Hit가 되겠죠?

---

### 슬라이드 19: 캐시 히트 & 캐시 미스

정리하면, 캐시 히트(Cache Hit)는 요청한 데이터가 캐시에 존재하여 원본 저장소에 접근하지 않고 바로 반환되는 경우이고,

캐시 미스(Cache Miss)는 요청한 데이터가 캐시에 존재하지 않아 원본 저장소에서 직접 데이터를 가져와야 하는 경우입니다.

냉장고에 딸기가 있으면 바로 꺼내먹고, 즉 Hit가 일어나고, 없으면 마트에 사러 가야 하는 것은 Miss라고 볼 수 있겠죠.

---

### 슬라이드 20: 캐시 적중률

그래서 캐시의 성능을 나타내는 지표가 있는데, '캐시 적중률' 즉 **Cache Hit Ratio**라고 해요.

공식은 간단하게 본다면, 전체 요청, 즉 캐시 히트 횟수 + 캐시 미스 횟수를 더한 것 중에 캐시 히트 횟수입니다.

예를 들어 100번의 요청 중 90번 캐시에서 응답했으면, Cache Hit Ratio = 90%가 되는 거예요.

높을수록 캐시 성능이 좋다는 의미라고 이야기할 수 있겠습니다.

### 슬라이드 21: 교체 정책 (Eviction Policy)

그런데 여기서 현실적인 문제가 하나 생깁니다.

캐시는 용량이 작다고 말씀드렸는데요, 그럼 꽉 찼을 때 어떤 데이터를 버려야 할까요?

이걸 결정하는 게 바로 **교체 정책입니다.**

대표적인 알고리즘 세 가지를 소개할게요.

첫 번째, **FIFO(First In First Out)**. 기준은 '입력 순서'예요. 선입선출이라고도 하는데요. 먼저 들어온 데이터를 먼저 제거하는 것으로, 가장 단순한 방식이에요.

두 번째, **LRU(Least Recently Used)**. 기준은 '최근 사용 시간'이에요. 가장 오랫동안 안 쓴 데이터를 제거합니다. 오래된 잡지처럼, 오랫동안 안 읽은 것부터 버리는 것입니다.

세 번째, **LFU(Least Frequently Used)**. 기준은 '사용 빈도', 즉 가장 적게 사용된 데이터를 제거합니다. 냉장고에서 거의 안 꺼내 먹는 음식부터 버리는 거예요.

---

### 슬라이드 22: 캐시 무효화 정책 (Cache Invalidation)

교체 정책 다음으로, **캐시 무효화 정책**에 대해 알아볼게요.

캐시에 저장된 기존의 오래된 데이터를 무효화, 즉 삭제하거나 갱신하여 사용자가 항상 최신 데이터를 볼 수 있도록 보장하는 프로세스입니다.

예를 들어, 여러분이 쇼핑몰에서 상품 가격을 봤는데, 캐시된 데이터라서 실제로는 이미 변경된 가격이 안 보이는 상황을 방지하는 거예요.

방법은 세 가지인데요.

첫 번째, **시간 기반 무효화 = TTL(Time To Live)**. 만료 시간을 설정해두고, 시간이 지나면 자동으로 캐시를 삭제하는 방식이에요. 예를 들어, '이 데이터는 1시간 뒤에 지워줘' 하는 거죠.

두 번째, **변경 기반 무효화**. 원본 데이터가 변경되는 순간을 감지해서 자동으로 업데이트하거나 삭제하는 방식이에요. 실시간성이 중요할 때 사용해요.

세 번째, **수동 무효화**. 필요에 따라 애플리케이션 로직을 통해 데이터를 수동으로 무효화하는 방식으로, 관리자가 직접 '이 캐시 지워!' 하는 것입니다.

### 슬라이드 23: 캐시 사용 사례(1) — CPU 캐시 메모리

이제 마지막으로 캐시가 실제로 어떻게 다양하게 사용되는지 사례를 살펴볼게요.

첫 번째는 **CPU 캐시 메모리입니다.**

CPU 캐시 메모리는 초고속 프로세서, 즉, CPU와 상대적으로 속도가 느린 메인 메모리 RAM 사이의 속도 차이를 줄여 병목 현상을 해결하는 임시 고속 메모리입니다.

CPU는 프로그램을 실행하기 위하여 메모리에서 데이터나 명령어를 가져오는데, CPU 성능이 아무리 빨라도 메모리에서 데이터를 받아오는 속도가 느리다면 성능을 활용할 수 없고, 병목이 생길 것입니다.

그래서 CPU 내부에 SRAM 기반의 초고속 메모리를 탑재하고, 자주 쓰는 데이터를 CPU 가까이에 미리 올려두는 거예요.

캐시 메모리는 **L1, L2, L3 캐시**가 계층을 이루어 구성하고 있답니다.

---

### 슬라이드 24: 캐시 사용 사례(2) — 데이터베이스 캐시

두 번째 사례는 **데이터베이스 캐시**예요.

DB(데이터베이스)는 데이터를 디스크에서 읽어오기 때문에 응답이 느립니다. 그리고 요청이 몰리면 DB 부하가 올라가서 서비스 전체가 느려질 수 있는데요.

그래서 자주 요청되는 쿼리 결과를 메모리에 올려두는 캐싱 전략을 사용해요.

대표적인 방식이 Redis 같은 캐시 서버를 DB 앞단에 두고, 요청이 오면 DB까지 가기 전에 Redis에서 먼저 응답하도록 구성하는 것입니다.

예를 들어, 배달 앱에서 '인기 메뉴 TOP 10' 같은 데이터는 수만 명이 동시에 요청할 수 있잖아요. 이런 걸 매번 DB에서 계산하면 너무 느리니까, Redis에 저장해두고 빠르게 읽을 수 있도록 하는 것입니다.

---

### 슬라이드 25: 캐시 사용 사례(3) — CDN

세 번째 사례는 **CDN, Content Delivery Network**예요.

CDN은 동영상, 이미지 등 웹 콘텐츠를 세계 곳곳에 있는 여러 서버에 분산하여 저장하는 분산 서버 네트워크 시스템이에요.

유튜브 서버는 미국에 있는데, 영상 하나하나를 볼 때마다 한국에서 매번 미국 서버까지 접속한다면 엄청 느리겠죠?

그래서 CDN은 전 세계 각지에 캐시 서버를 분산 배치해서, 사용자와 가까운 서버에서 콘텐츠를 제공하는 방식을 제공하고 있습니다.

그래서 여러분이 유튜브에서 영상을 볼 때, 사실 미국 서버가 아니라 한국에 있는 엣지 서버(Edge Server)가 응답하고 있을 가능성이 높은데요,

Cloudflare, AWS CloudFront, Google Cloud CDN 등이 대표적인 CDN이에요.

---

### 슬라이드 26: 캐시 사용 사례(4) — 웹 캐시 (브라우저 캐시)

네 번째, 마지막 사례는 **웹 캐시 중에서도 브라우저 캐시인데요**.

웹사이트 접속 시 HTML, CSS, JS, 이미지를 로컬 디스크에 저장해두고 재활용하는 방식이에요.

여러분이 자주 들어가는 사이트에 두 번째 방문할 때 처음보다 확실히 빠르게 뜨는 경험, 해보시지 않으셨나요? 그게 바로 브라우저 캐시 덕분이에요!

브라우저 캐시는 두 종류로 나뉘어요.

**memory cache**는 RAM에 저장되고, 브라우저를 종료하면 사라집니다.

**disk cache**는 SSD에 저장되고, 브라우저를 종료한 후에도 유지돼요.

슬라이드에 있는 크롬 개발자 도구 화면에서 저 빨간 박스 네트워크 탭에 들어가면, 오른쪽에 (memory cache), (disk cache) 라고 파란 박스와 초록 박스로 표시된 게 보이시죠? 저게 바로 브라우저가 캐시에서 응답하고 있다는 표시입니다.

---

### 슬라이드 27: 정리

자, 오늘 배운 내용을 간단하게 정리해볼게요!

캐시는 자주 사용하는 데이터를 빠른 곳에 미리 복사해두는 임시 저장소였죠. 딸기 냉장고처럼요!

캐시 히트는 캐시에 데이터가 있어서 바로 반환되는 경우, 캐시 미스는 없어서 원본 저장소까지 가야 하는 경우.

캐시가 가득 찼을 때는 교체 정책(FIFO, LRU, LFU)으로 어떤 걸 버릴지 결정하고, 오래된 데이터는 무효화 정책(TTL, 변경 기반, 수동)으로 최신 상태를 유지해요.

그리고 캐시는 CPU 메모리, DB 캐시, CDN, 브라우저 캐시 등 우리 일상 곳곳에서 사용되고 있어요.

여러분이 오늘 유튜브를 보거나, 웹사이트에 접속할 때, '아, 지금 캐시가 동작하고 있겠구나!' 하고 한번 떠올려보시면 좋을 것 같습니다.
