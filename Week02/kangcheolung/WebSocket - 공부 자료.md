# 1. WebSocket이 왜 필요한가?

## HTTP의 한계 — 왜 실시간이 어려운가?

- HTTP는 **클라이언트가 요청해야만** 서버가 응답할 수 있다
- 응답이 오면 **연결이 끊긴다** → 매번 새로 연결해야 함
- 즉, 서버가 먼저 클라이언트에게 데이터를 보내는 것이 **불가능**

## Polling — HTTP로 실시간을 흉내내면?

- HTTP의 한계를 우회하기 위해 **일정 주기마다 계속 요청**을 보내는 방식
- 실시간처럼 보이지만 사실은 **"계속 물어보는 것"**
- 사용자가 늘어날수록 서버 요청이 폭발적으로 증가

# 2. SSE vs WebSocket

## WebSocket이란?

- **한 번 연결하면 연결을 유지**하면서 양방향 통신이 가능한 프로토콜
- 서버가 먼저 클라이언트에게 데이터를 보내는 것도 가능
- 연결을 맺는 비용이 한 번뿐이라 **Polling보다 훨씬 효율적**
- 최초 연결 시 HTTP로 시작해 WebSocket 프로토콜로 업그레이드한다 **(핸드셰이크)**

예시: 실시간 채팅, 실시간 협업

## SSE(Server-Sent Events)란?

- 서버 → 클라이언트 **단방향** 실시간 통신 방식
- HTTP 위에서 동작하기 때문에 별도 프로토콜 없이 구현이 **간단**
- 연결을 유지하면서 서버가 **이벤트를 스트림 형태로 push**
- 클라이언트는 연결만 해놓으면 서버가 데이터를 보낼 때마다 **자동으로 수신**
- 클라이언트가 서버에 뭔가를 보낼 필요가 없는 경우에 적합

> 예시: 가격 변동 알림, 뉴스피드 업데이트, 배달 상태 알림
> 

## 정리

## SSE vs WebSocket

| 구분 | SSE | WebSocket |
| --- | --- | --- |
| 통신 방향 | 서버 → 클라이언트 (단방향) | 서버 ↔ 클라이언트 (양방향) |
| 프로토콜 | HTTP | `ws://` (별도 프로토콜) |
| 구현 복잡도 | 간단 | 복잡 |
| 자동 재연결 | 브라우저가 기본 지원 | 직접 구현 필요 |
| 적합한 용도 | 알림, 피드, 가격 변동 | 채팅, 게임, 실시간 협업 |

> **선택 기준:**
> 
> 
> 서버만 보내면 되는 상황 → SSE
> 
> 클라이언트도 서버에 데이터를 보내야 하는 상황 → WebSocket
>

# STOMP

## 순수 WebSocket의 문제

- 순수 WebSocket은 **형식이 없는** 날것의 문자열 채널
- 메시지만 덩그러니 오기 때문에 **누가 보냈는지, 무슨 행동인지, 어디로 가야 하는지** 알 수 없음
- 서버가 직접 모든 파싱 로직을 만들어야 한다
- 특정 주제를 구독 중인 사용자들에게 메시지를 뿌려주는 **Pub/Sub 기능이 없음** → 세션 그룹 관리를 직접 구현해야 함

## STOMP란?

- **STOMP(Simple Text Oriented Messaging Protocol)**
- WebSocket 위에서 동작하는 **메시징 표준 규칙**
- 모든 메시지에 **목적지(destination)** 와 명령어가 붙어서 의미가 명확해진다

## STOMP — Destination이란?

- STOMP에서 모든 메시지에는 **목적지(Destination)** 가 붙는다
- 메시지가 **어디서 왔고, 어디로 가야 하는지** 를 나타내는 주소
- Spring은 이 목적지를 보고 **자동으로 적절한 처리**를 한다
- 목적지는 크게 `/app`과 `/topic` 두 가지로 나뉜다

`/app/chat/room/1    ← 클라이언트가 서버에 메시지 처리를 요청
/topic/chat/room/1  ← 해당 토픽 구독자 전원에게 메시지 전달`

## STOMP — Destination: `/app`

- 클라이언트 → 서버 방향
- 클라이언트가 서버에 **처리를 요청**할 때 사용
- 클라이언트는 `send()`로 전송, 서버는 `@MessageMapping`으로 수신

`/app/chat/room/1  ← 클라이언트가 1번 채팅방에 메시지 전송 요청`

---

## STOMP — Destination: `/topic`

- 서버 → 클라이언트들 방향
- 서버가 **구독자 전원에게 동시에 전달**할 때 사용 (브로드캐스트)
- 클라이언트는 `subscribe()`로 구독, 서버는 `convertAndSend()`로 전송

`/topic/chat/room/1  ← 서버가 1번 채팅방 구독자 전원에게 브로드캐스트`

## 4. 브로드캐스트(Broadcast)란?

- **한 명의 행동을 구독 중인 여러 명에게 동시에 전달**하는 것
- HTTP 응답은 요청한 사람에게만 1:1로 돌아가지만, 브로드캐스트는 **1:N**
