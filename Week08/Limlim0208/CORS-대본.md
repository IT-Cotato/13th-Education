### 3페이지 — 웹의 Origin Policy(1)

CORS를 이해하려면 먼저 웹의 Origin, 출처라는 개념부터 정확히 알아야 합니다.

출처는 프로토콜, 호스트, 포트 이 세 가지 요소로 구성됩니다. 이 셋 중 하나라도 다르면 브라우저는 완전히 다른 출처로 취급하는데요.

### 4페이지 — 웹의 Origin Policy(2)

예를 들어 화면의 이 두 가지 URI의 도메인은 같지만, 프로토콜이 **https**와 **http**로 서로 다릅니다.

그렇기 때문에 브라우저는 이 두 주소를 서로 다른 출처로 인식합니다.

### 5페이지 — 웹의 Origin Policy(예시)

저희 코테이토의 홈페이지 주소로 한번 출처가 같은지 비교해보는 예제를 가지고 와봤는데요.

첫번째와 두번재 경우처럼 프로토콜, 도메인, 포트가 같은 주소는 같은 출처라고 볼 수 있습니다.

HTTPS의 기본 포트인 443은 생략이 가능하고, 경로는 출처에 포함되지 않기 때문입니다.

그 외 각각 프로토콜, 도메인, 포트가 하나라도 다르면 전부 다른 출처가 됩니다.

이 출처는 브라우저가 어떤 웹 페이지에서 서버로 리소스를 요청할 때.

"이 요청을 보낸 출처가 어디인지"를 확인하기 위해 항상 사용되는데요.

그렇다면, 기준이 되는 출처에서 다른 출처로 리소스 요청을 보낸다면, 과연 어떤 일이 일어날까요?

---

### 6페이지 — 다른 출처에 리소스를 요청하면?(1)

여기 두가지 URL이 있습니다. 하나는 `https 코테이토 . kr` 이라는 출처이고, 하나는 `https [토마토.kr](http://토마토.kr)` 이라는 출처인데요.

여기서 코테이토 출처를 가진 웹 애플리케이션에서 토마토 출처의 리소스를 한번 요청해보겠습니다. 그쪽의 토마토 좀 달라고요.

### 7페이지 — 다른 출처에 리소스를 요청하면?(2)

토마토 출처에서는 이 리소스 요청에 응답합니다.

그런데, 코테이토 출처의 브라우저는 그 응답을 스크립트가 읽지 못하도록 차단해버립니다.

### 8페이지 — 다른 출처에 리소스를 요청하면?(3)

결국 다른 출처에 리소스를 요청해봤더니, 브라우저에서 CORS 에러가 발생하고 말았습니다.

그러면 왜 이런 오류가 발생하는 걸까요?

---

### 9페이지 — SOP

그 이유는 바로 웹 브라우저에서 사용하는 **동일 출처 정책** 때문입니다.

SOP는 Same-Origin Policy의 줄임말로, 직역하자면 **동일 출처 정책**을 의미하는데요.

즉, 동일 출처만을 허용하고, **서로 다른 출처일 때** 리소스 요청과 응답을 **차단**하는 정책을 말합니다.

코테이토 출처와 토마토 출처가 서로 다른 출처이기 때문에 리소스 요청과 응답을 차단해버린 겁니다.

### 10페이지 — SOP 특징

브라우저는 기본적으로 다른 서버를 신뢰하지 않습니다. 때문에, 다른 서버에 리소스 요청을 보내거나 응답을 받는 걸 차단합니다.

토큰, 쿠키와 같이 민감한 사용자 정보는 브라우저에 저장되는데, 이 정보를 탈취하면 심각한 보안 이슈가 생기기 때문입니다.

이와 같은 문제를 막기 위해, 서로 다른 서버 리소스는 공유하지 않는 브라우저 정책을 SOP, 동일 출처 정책이라고 합니다.

---

### 11페이지 — 웹의 발달과 CORS

그런데 이 SOP만으로는 요즘 웹 개발 방식과 잘 맞지 않는 부분이 생겼습니다.

과거에는 프론트엔드와 백엔드를 따로 구성하지 않고 하나의 서버에서 함께 처리하는 구조가 많았어요.

그러다 보니 모든 처리가 같은 도메인 안에서 이루어졌고, 다른 출처로 요청을 보내는 행위 자체가 의심스러운 상황으로 여겨질 수밖에 없었습니다.

하지만 지금은 다릅니다.

클라이언트에서 API를 직접 호출하는 방식이 당연해졌고, 여러분께서 진행하고 계실 프로젝트에서도 프론트엔드와 백엔드 API가 서로 다른 도메인에 배포되어 있는 경우가 대부분이죠.

그래서 출처가 다르더라도 필요한 경우에는 안전하게 요청과 응답을 주고받을 수 있는 방법이 필요해졌습니다.

### 12페이지 — 웹의 발달과 CORS

그 결과, 등장한 정책이 바로 CORS입니다.

### 13페이지 — CORS

CORS는 `Cross-Origin 리소스 셰어링`의 약자로 직역하자면 **교차 출처 리소스 공유**입니다.

즉 서로 다른 출처라도 “서버가 허락한 범위 안에서는” 리소스 요청과 응답을 주고받을 수 있게 허락 해주는 정책입니다.

그럼, 브라우저는 리소스를 요청한 출처가 서버에서 허락한 출처가 맞는지 어떻게 확인하는 걸까요?

이걸 확인하는 과정을 총 4단계로 정리해봤는데요.

### 14페이지 — 브라우저가 CORS를 확인하는 방법(1)

먼저 브라우저가 요청을 보낼 때 헤더에 자신의 출처 정보를 담은 `Origin` 헤더를 함께 보냅니다. 

### 15페이지 — 브라우저가 CORS를 확인하는 방법(2)

그러면 서버는 응답 헤더에 `Access-Control-Allow-Origin`이라는 값을 담아서 돌려줘요. 

여기서 이 값은, 서버가 리소스 요청을 허용할 출처를 명시하는 응답 헤더입니다.

### 16페이지 — 브라우저가 CORS를 확인하는 방법(3)

그럼 브라우저는 서버가 보낸 값을 받아서,

자기가 보낸 Origin과

서버가 허용한다고 응답한 Access-Control-Allow-Origin 값을

서로 비교합니다.

### 17페이지 — 브라우저가 CORS를 확인하는 방법(4)

만약 서버가 허용한 목록 안에 요청을 보낸 출처가 포함되어 있지 않으면,  브라우저는 콘솔에 CORS 에러를 띄웁니다.

브라우저가 응답을 받고도 스크립트에 결과를 넘겨주지 않아서 응답 결과를 읽지 못하게 차단하는 겁니다.

여기서 한 가지 헷갈리기 쉬운 부분이, 서버와 클라이언트 간의 소통 결과인데요.

본 요청이 서버까지 도달하는 경우에는, 서버 입장에는 이 요청에 정상적으로 응답을 했기 때문에

서버 로그에는 성공으로 기록됩니다

즉 CORS 에러는 서버가 요청을 거부한 게 아니라, **브라우저가 응답을 받은 후에 스스로 걸러내는 것**이라는 점을 꼭 기억해 주세요.

다만 이 동작 방식이 요청 종류에 따라 조금씩 달라지는데요. 바로 다음 페이지에서 이어서 살펴보겠습니다.

### 19페이지 — 사전 요청(Preflighted requests)(1)

먼저 사전 요청입니다. 실제 프로젝트에서 API를 호출할 때 가장 많이 마주치게 되는 방식이 바로 이 사전 요청인데요.

브라우저가 본 요청을 하기 전에 Preflight Request(사전 요청)를 보내 서버와 잘 통신할 수 있는지 확인하는 방식을 말합니다.

PPT의 이미지를 보시면 전체 흐름을 파악하실 수 있는데요.

먼저 우리가 fetch()로 리소스를 요청하면, 브라우저는 실제 요청을 보내기 전에 먼저 OPTIONS 메서드로 예비 요청을 보냅니다.

이때 요청 헤더에는 자신의 출처를 담은 Origin,
그리고 실제 요청에서 사용할 메서드와 헤더를 각각 
Access-Control-Request-Method, Headers에 담아 보내요.

서버는 이 예비 요청에 대한 응답으로, 자신이 허용하는 출처·메서드·헤더 목록을 
Access-Control-Allow-Origin, Methods, Headers에 각각 담아서 돌려줍니다.

브라우저는 이 응답을 자신이 보낸 요청과 비교해서 안전하다고 판단되면, 그제서야 실제 본 요청을 보냅니다.

### 20페이지 — 사전 요청(Preflighted requests)(2)

사전 요청 방식의 특징은

HTTP 메소드가 GET이나 POST가 아닌 OPTIONS라는 요청이 사용된다는 점입니다.

그리고 단점은요청마다 예비 요청이 추가로 발생해서

실제 요청까지 걸리는 시간이 늘어난다는 점인데요.

이 문제를 완화하기 위해  `Access-Control-Max-Age`를 활용해서 예비 요청 결과를 캐싱해두는 방법을 쓸 수 있습니다.

Access-Control-Max-Age 헤더에 캐시될 시간을 명시해 주면,

이 사전 요청을 브라우저에 캐싱시켜 최적화를 할 수 있습니다.

캐싱 시간은 초 단위로 설정이 가능한데요. 브라우저마다 설정할 수 있는 시간의 상한이 다릅니다.

예를 들어 크롬과 마이크로 소프트는 최대 2시간, 사파리는 5분까지 데이터를 캐싱해둘 수 있습니다.

### 21페이지 — **단순 요청 (Simple Requests)**(1)

다음 CORS 동작 방식은 단순 요청입니다.

이 방식은 사전 요청 없이 바로 본 요청을 보내고, 서버 응답 헤더만으로 CORS 위반 여부를 검사하는 방식인데요.

### 22페이지 — **단순 요청 (Simple Requests)**(2)

다만 이렇게 동작하려면 화면에 정리된 세 가지 조건을 모두 만족해야 합니다.

첫째, 요청 메서드가 GET, HEAD, POST 중 하나여야 하고요.

둘째, 사용하는 헤더가 다음 표준 헤더 범위 안에 있어야 하는데요

Accept·Accept-Language·Content-Language·Content-Type은

콘텐츠를 어떤 형식과 언어로 주고받을지에 대한 헤더입니다.

DPR·Downlink·Save-Data·Viewport-Width·Width는 클라이언트 환경, 즉 화면 크기와 네트워크 상태에 맞춰 최적화된 리소스를 요청하기 위한 헤더입니다.

마지막으로, Content-Type이 다음 세 타입 중 하나여야 하는데요.

그런데 사실 이 조건을 실무에서 다 만족하기는 쉽지 않습니다.

왜냐하면 대부분의 API는 json 방식으로 데이터를 주고받는데, 이건 세 번째 조건에 해당하지 않기 때문입니다.

그래서 결과적으로, 우리가 자주 마주칠 API 요청의 대부분은

앞에서 살펴본 사전 요청 방식으로 처리된다고 보시면 됩니다.

### 23페이지 — 자격 증명 요청 (Credentialed Request)(1)

마지막으로 자격 증명 요청 방식입니다.

이 방식은 클라이언트가 서버에게 세션 쿠키나 Authorization 토큰 같은 **인증 정보**를 함께 실어서 요청할 때 사용되는 방식입니다.

이는 기존의 단순 요청이나 사전 요청과는 살짝 다른 인증 형태로 통신하게 되는데요.

클라이언트 측과 서버 측에서 각각 다른 설정이 필요합니다.

### 24페이지 — 자격 증명 요청 (Credentialed Request)(2)

먼저 클라이언트 쪽에서는 `크리덴셜즈`라는 옵션을 설정해야 합니다. 해당 옵션에는 총 3가지 값이 있는데요.

기본값인 `세임 오리진`은 같은 출처 요청에만 인증 정보를 담고, `인클루드`로 설정하면 다른 출처로 보내는 요청에도 인증 정보를 포함시킬 수 있어요. 반대로 `오밋`은 아예 인증 정보를 담지 않습니다.

화면의 코드는 `fetch` 메서드를 사용할 때 예시 코드인데요. 화면의 코드처럼 `크리덴셜즈: "인클루드"`를 명시해줘야 다른 출처로 쿠키 같은 인증 정보가 전달됩니다.

별도 설정이 없으면 인증 정보는 절대로 자동 전송되지 않으니 유의해야합니다.

### 25페이지 — 자격 증명 요청 (Credentialed Request)(3)

서버 쪽에서도 이 인증된 요청에 맞게 응답을 구성해야 하는데요, 여기서 중요한 제약이 있습니다.

응답 헤더의 `액세스-컨트롤-얼로우-크리덴셜즈`를 반드시 `true`로 설정해야 하고,

`엑세스-컨트롤-얼로우-오리진`에는 와일드카드 `*`를 쓸 수 없고 반드시 명시적인 URL을 지정해야 해요.

`얼로우-메소드즈` 와`얼로우-헤더즈`도 마찬가지로 와일드카드를 쓸 수 없습니다.

인증 정보는 민감한 정보이기 때문에 출처를 명확하게 지정하도록 강제하는 거죠.

위 두 조건 중 하나라도 어긋나면 브라우저가 CORS 정책 위반으로 응답을 거부합니다. 그럼 앞에서 봤던 CORS 에러가 발생하는 거죠!

이렇게 CORS 에러가 발생했을때 대응할 수 있는 방법은 2가지가 있습니다.

---

### 26페이지 — CORS 에러 대응하기(1)

먼저 첫번째는 서버에서 `엑세스-컨트롤-얼로우-오리진` 헤더를 설정하는 방법입니다.

서버에서 해당 헤더를 설정하면, 요청을 수락할 출처를 명시적으로 지정할 수 있는데요. 다른 출처에서 리소스 요청이 오면 그 요청을 허용할 수 있습니다.

와일드카드를 설정하면 출처에 상관없이 모든 요청을 리소스에 접근할 수 있도록 설정하기 때문에 보얀에 취약해지게 됩니다.

### 27페이지 — CORS 에러 대응하기(2)

그래서 화면과 같이 리소스 요청을 수락할 출처를 직접 명시하는 방법이 더 안전합니다.

### 28페이지 — CORS 에러 대응하기(3)

CORS 에러에 대응하는 두 번째 방법은 프록시 서버를 사용하는 방법입니다.

웹 애플리케이션이 리소스를 직접적으로 요청하는 대신, **프록시 서버**를 사용하여 웹 애플리케이션에서 리소스로의 요청을 전달하는 것인데요.

예시를 통해 살펴보면, 웹 애플리케이션이 직접  API주소에 API를 요청하는 대신, 같은 출처에 위치한 프락시 서버를 통해 API 요청을 중계하도록 구성되어 있습니다.

결과적으로 이 방법을 사용하면, 웹 애플리케이션이 리소스와 동일한 출처에서 요청을 보내는 것처럼 보이기 때문에 CORS 에러를 방지할 수 있습니다.
