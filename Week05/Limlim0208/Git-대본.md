### 3페이지 — [API란?]

먼저 API가 무엇인지부터 알아보도록 하겠습니다. API는 Application Programming Interface(어플리케이션 프로그래밍 인터페이스)의 약자입니다.

애플리케이션이 데이터를 교환하고, 작업을 수행하고, 잘 문서화된 방식으로 상호작용할 수 있도록 지원하는 규칙과 프로토콜의 집합을 말합니다.

API는 백엔드에서 프론트엔드와 통신하기 위한 일반적인 메커니즘이기도 한데요.

그런데 이렇게만 이야기하면, 사실 이해가 잘 되지 않을 수 있을 것 같아요.
API가 어떻게 사용되는지, 식당으로 비유해서 생각해보도록 하겠습니다.

오늘날 웹에서 가장 많이 사용되고, 유연하게 사용되는 아키텍처 스타일입니다.

그럼 이제 REST API의 특징에 대해서 구체적으로 알아볼 차례인데요.

### 8페이지 — [REST란?]

REST는 **레프리젠테이셔널 / 스테이트 / 트랜스퍼**의 약자인데요.

REST는 네트워크 상에서 클라이언트와 서버 사이의 통신 방식 중 하나입니다.
특징적인 점은, REST는 API가 작동할 때, 여기에 조건을 부과한다는 점입니다.

REST는 자원을 URI라는 고유한 이름으로 식별하고,
그 자원의 상태를 표현이라는 형태로 주고받도록 하는 방식입니다.

즉, **레프리젠테이셔널 / 스테이트 / 트랜스퍼**를 풀어보면,
자원의 상태를 특정한 표현으로 전달한다는 뜻입니다.
이는 REST를 직역한 것과 같은 의미입니다.

REST는 2000년대 초에 등장한 개념으로, 웹의 장점을 최대한 활용하기 위해 만들어진 아키텍처 스타일입니다.

최근의 서버 프로그램은 다양한 브라우저와
안드로이폰, 아이폰과 같은 모바일 디바이스에서도 통신을 할 수 있어야 하는데요.

이러한 멀티 플랫폼에서도 서비스를 자원하기 위한 방법을 모색한 결과,
많은 개발자들이 REST에 관심을 가지게 되었습니다.

### 9페이지 — [REST의 구성요소]

REST는 총 세가지 요소로 구성되어 있는데요.
자원, 행위, 표현입니다. 각각 어떠한 특징이 있는지 알아보도록 하겠습니다.

**첫번째 요소는 자원입니다.**
이 자원은 서버에 존재하고, 모든 자원에는 고유한 ID가 존재합니다.
이 ID를 URI라고 합니다. 클라이언트는 URI를 통해 원하는 자원을 지정할 수 있습니다.
예시로 코테이토 출석 페이지의 URI를 가져왔는데요. 이런 식으로 웹 주소와 비슷한 형태입니다.

**두 번째 요소는 행위입니다.**
URI로 지정한 자원에 무엇을 할 것인지는 HTTP 메서드로 표현하는데요.
조회는 GET, 생성은 POST, 전체 수정은 PUT, 일부 수정은 PATCH, 삭제는 DELETE입니다.
데이터의 기본적인 처리 기능인, CRUD 연산과 대응된다고 보시면 됩니다.

**마지막 요소는 표현입니다.**
이는 클라이언트와 서버가 데이터를 주고받는 형태인데요.
일반적으로 JSON이나 XML 형식을 사용합니다.

### 10페이지 — [REST의 원칙]

REST를 기반으로 API를 제작할 때,
지켜야하는 원칙에는 다음과 같은 여섯가지 항목들이 있습니다.

간단히 살펴보도록 하겠습니다.

**먼저 첫번째, 균일한 인터페이스입니다.**
REST는 클라이언트와 서버 간의 통신을 단순화하고 표준화하기 위한 것을 목표로 합니다.

**두번째는 무상태성입니다.**
각 요청 간에 클라이언트의 상태 정보가 서버에 저장되지 않아야 합니다.

세션 정보나 쿠키정보를 별도로 저장하고 관리하지 않기 때문에
API 서버는 들어오는 요청만을 단순히 처리하면 됩니다.

때문에 서비스의 확장성이 높아지고,
서버에서 불필요한 정보를 관리하지 않음으로써 서버의 부하도 줄어듭니다.

**세번째는 서버-클라이언트 구조입니다.**

REST 서버는 API를 제공하고,
클라이언트는 사용자 인증이나 세션, 로그인 정보등을 직접 관리하는 구조로
각각의 역할이 확실히 구분되어야 합니다.

그 결과, 클라이언트와 서버 간에 개발해야 하는 내용이 명확해지고. 서로간 의존성이 줄어들게 됩니다.

**네번째는 캐시가능성입니다.**
클라이언트는 응답을 캐싱할 수 있어야 하며, 이는 네트워크 효율성을 향상시킬 수 있습니다.

**다섯 번째는 계층 구조입니다.**
클라이언트는 자신이
직접 연결된 서버 또는 중간 레이어에 있는 서버와 통신하는지 알 수 없습니다.
이러한 계층화는 시스템의 확장성을 향상시킬 수 있습니다.

**그리고 마지막은 온디맨드 코드입니다.**
이 항목은 선택적 사항인데요.
서버는 소프트웨어 프로그래밍 코드를 클라이언트에 전송하여
클라이언트 기능을 일시적으로 확장하거나 사용자 지정할 수 있습니다.

### 24페이지 — [REST API 설계 기본 규칙(1)]

핵심 원칙은 두 가지입니다.

첫째, URI는 정보의 자원을 표현해야 하고,
둘째, 자원에 대한 행위는 HTTP Method로 표현한다는 것입니다.

이때, 이 행위는 URI에 포함하지 않습니다.

---

### 25페이지 — [REST API의 설계 규칙(2)]

다음으로 이어지는 설계규칙에 대해 알아보겠습니다.

**첫 번째, URI는 명사를 사용해야 합니다.**

 `/겟-세트 메뉴스`처럼 동사를 쓰는 게 아니라,
`/세트 메뉴`처럼 자원의 이름, 즉 명사만 씁니다.
어떤 행위를 할지는 HTTP 메서드가 담당하거든요.

**두 번째, 슬래시로 계층 관계를 표현합니다.**

컴퓨터 폴더 구조처럼
세트메뉴 안에 2번 세트메뉴가 들어있고,
2번 세트 안에 구성항목들이 들어있는 것처럼
계층을 생각하시면 좋습니다.

URI는 이런 계층을 `/세트 메뉴스(슬래시)2(슬래시)아이템즈(슬래시)3` 처럼 슬래시를 사용해 표현합니다.

**세 번째, URI 마지막에는 슬래시를 붙이지 않습니다.**

첫번째 예시와 두번째 예시의 차이점이 뭘까요?
바로, 첫번째 예시의 끝에는 슬래시가 붙어있고, 두번째 예시의 끝에는 슬래시가 붙어있지 않습니다.

이처럼 URI의 마지막 문자로는 슬래시를 작성할 수 없는데요.
불필요한 슬래시는 혼란을 줄 수 있기 때문입니다.

**네 번째, 밑줄 대신 하이픈을 사용합니다.**

가독성을 위해 단어를 구분할 때 언더바(`_`) 대신 하이픈(`-`)을 씁니다.
컴퓨터는 언더바(_)가 있으면 폰트에 따라 언더바가 밑줄에 가려져 잘 안보일 수 있기 때문입니다.

**다섯 번째, URI는 소문자로만 구성합니다.**

대문자로 쓰인 URI와 소문자로 쓰인 URI는
서버 입장에서 다른 자원으로 인식될 수 있습니다.
그렇기 때문에, URI는 항상 소문자로만 써야합니다.

**여섯 번째, 파일 확장자는 URI에 포함하지 않습니다.**

`/photo.jpg`처럼 확장자를 붙이지 않고, `/photo`로만 표현합니다.
어떤 형태로 받을지는 따로 명시하면 되거든요.

### 26페이지 — [REST API의 설계 규칙(3)]

마지막으로 두 가지 설계규칙이 남았습니다.

**일곱 번째, HTTP 응답 상태 코드를 사용합니다.**

음식을 주문했는데 점원이 아무 말 없이 사라지면 곤란하겠죠.
음식이 나왔는지, 품절인지, 아니면 주문서를 잘못 작성한 건지 피드백이 꼭 있어야 합니다.

REST API도 마찬가지입니다.
성공하면 200, 없는 메뉴를 조회하면 404, 서버에 문제가 생기면 500을 돌려주는 식으로
클라이언트에게 응답이 어떤 상태인지 알려줍니다.

**마지막으로, 정보를 조회할 때 쿼리를 사용한다는 점입니다.**

한 가지 예시를 가져왔는데요.
총 20개의 메뉴가 있을 때 다음의 코드를 사용해 특정 메뉴를 조회한다고 생각해보겠습니다.

이때, page=2 라는 코드는 두번째 페이지를 보여달라는 의미이고,
count=5 라는 코드는 한 페이지에 메뉴를 5개씩 보여달라는 의미입니다.

결과적으로, 사용자는 6번에서 10번 메뉴를 조회할 수 있습니다.

### 27페이지 - RESTful API 코드예시(1)

이런 설계규칙을 잘 지켰을 때의 장점은 코드에서도 확인할 수 있는데요.

`GET /set-menus` 라는 명령어만 봐도 '세트 메뉴 목록을 요청하는구나'를 바로 알 수 있죠.
`GET /set-menus/1` 는 그 중 1번, A세트의 상세 정보가 오고요.

### 28페이지 - RESTful API 코드예시(2)

`GET /set-menus/1/items`는 A세트의 구성 항목 목록을 확인할 수 있습니다.
`GET /set-menus/1/items/3` 은 그 중 3번 항목인 음료의 상세 정보까지 가져올 수 있습니다.

**이처럼 RESTful하게 만든 API는
요청 주소만 봐도 무엇을 요청하는지 바로 파악**할 수 있다는 것이 가장 큰 특징입니다.

반대로 규칙을 제대로 지키지 않은 API는
REST API라고 부를 수는 있지만
RESTful하다고는 하지 않습니다
