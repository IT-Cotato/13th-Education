## 슬라이드 1

안녕하세요! 이번주 CS 교육을 맡은 13기 백엔드 배선아입니다.

오늘의 교육 주제는 CI/CD인데요, 오늘 CI/CD를 통해 우리가 작성한 코드가 어떻게 실제 사용자에게 도착하는지 알아보겠습니다. 

CI/CD 아마 다들 프로젝트에서 도입하고 계실텐데요.

오늘은 단순히 개념을 익히기 보다, 코드가 변경된 순간부터 실제 운영 환경에 배포되기까지 어떤 과정이 이어지는지를 전체 흐름 중심으로 살펴보시면 좋을 것 같습니다.

---

## 슬라이드 2

오늘 교육 목표는 네 가지입니다. 

먼저 CI와 CD의 개념과 차이, 

CI/CD 파이프라인의 동작 과정,

환경별 배포와 배포 전략,

안전한 배포를 위한 고려 사항 순으로 살펴보겠습니다.

---

## 슬라이드 3

먼저 이런 상황을 하나 가정해 보겠습니다.

금요일 오후 5시에 “로그인 수정 사항을 오늘 안에 반영해 주세요”라는 요청이 들어왔습니다.

개발자는 개발은 끝났지만 코드 병합, 테스트, 빌드, 서버 반영, 최종 확인이 아직 남아 있습니다.

이 과정을 사람이 매번 직접 수행하면 작은 단계가 실수로 빠지거나, 사람마다 다른 순서로 작업할 수 있는 문제가 발생하게 됩니다.

즉, 코드를 작성하는 것만큼이나 작성한 코드를 안전하게 전달하는 과정도 중요합니다.

---

## 슬라이드 4

그래서 이 반복 작업을 일정한 절차로 대신 수행해 줄 방법이 필요한데요.

그 방법이 바로 CI/CD입니다.

CI는 변경된 코드를 기존 코드에 합쳐도 되는지 검증하는 과정이고, CD는 검증된 결과물을 원하는 환경에 전달하는 과정입니다.

여기서 중요한 점은 CI/CD의 목적이 무조건 빠르게 배포하는 것이 아니라, 같은 절차를 반복해서 더 자주, 더 안전하게 전달하는 것입니다.

---

## 슬라이드 5

그렇다면 CI는 정확히 무엇을 하는 걸까요?

CI는  Continuous Integration의 약자로, 지속적 통합을 의미합니다.

여러 사람이 각자의 브랜치에서 작업한 코드를 기준 브랜치인 main 브랜치로 자주 합치고, 합칠 때마다 테스트와 빌드 같은 검증을 자동으로 수행합니다.

만약 변경 크기가 작으면 문제가 발생했을 때 확인해야 할 범위도 작아집니다.

---

## 슬라이드 6

그런데 왜 굳이 코드를 자주 합쳐야 할까요?

여러 사람이 오랫동안 작업한 코드를 마지막에 한꺼번에 합치면, 변경 사항이 서로 얽혀 충돌 원인을 찾기 어렵습니다.

반대로 작은 변경을 자주 통합하면 문제가 발생해도 최근 변경만 확인하면 되겠죠.

코드를 자주 통합한다고 충돌이 완전히 사라지는 것은 아니지만, 문제가 커지기 전에 더 빨리 발견하고 작은 범위에서 해결할 수 있습니다.

---

## 슬라이드 7

이제 이러한 자동 검증이 언제 시작되는지 알아보겠습니다.

파이프라인은 특정 이벤트를 계기로 실행되며, 이 시작 조건을 Trigger라고 합니다.

Pull Request가 생성됐을 때, 특정 브랜치에 코드가 Push됐을 때, 정해진 시간이 됐을 때 또는 사용자가 직접 실행했을 때 시작할 수 있습니다.

즉, 파이프라인은 계속 실행되는 것이 아니라 미리 정한 사건이 발생했을 때 동작합니다.

---

## 슬라이드 8

모든 이벤트에서 전체 작업을 실행할 필요는 없는데요.

Pull Request에서는 빠른 검사로 병합 가능 여부를 확인하고, main 브랜치에 반영되면 스테이징 환경에 배포할 수 있습니다.

실제 사용자에게 영향을 주는 운영 배포는 버전 태그나 수동 승인처럼 더 제한된 조건에서 실행할 수 있습니다.

버전 태그는 쉽게 말해서 “이 버전을 배포하겠다”하고 표시하는 것이고, 이벤트마다 목적이 다르기 때문에 실행되는 작업도 달라집니다.

---

## 슬라이드 9

이제 파이프라인 내부 구조를 살펴보겠습니다.

GitHub Actions에서는 전체 자동화 흐름을 Workflow라고 하는데,

Workflow 안에는 프론트엔드 테스트나 백엔드 빌드처럼 목적별 작업 묶음인 Job이 있습니다.

그리고 Job 안에서 코드를 가져오고, 패키지를 설치하고, 테스트를 실행하는 각각의 작업을 Step이라고 합니다.

정리하면 Workflow는 전체 흐름, Job은 작업 묶음, Step은 실제 실행 단위라고 할 수 있습니다.

---

## 슬라이드 10

여러 Job이 항상 하나씩 순서대로 실행될 필요는 없습니다.

프론트엔드 테스트와 백엔드 테스트처럼 서로의 결과를 기다릴 필요가 없는 작업은 동시에 실행할 수 있습니다.

이를 병렬 실행이라고 하는데요.

만약 프론트 테스트와 백엔드 테스트 이 두 작업을 순서대로 실행하면 90초가 필요하지만, 동시에 실행하면 더 오래 걸리는 작업이 끝나는 약 50초 후에 전체 작업이 완료됩니다.

즉, 독립적인 작업을 병렬로 실행하면 파이프라인의 대기 시간을 줄일 수 있습니다.

---

## 슬라이드 11

그렇다면 CI는 무엇을 검사할까요?

대표적으로는 코드 스타일을 확인하는 Lint, 기능을 확인하는 Test, 실행 가능한 결과물이 만들어지는지 확인하는 Build가 있습니다.

필요하다면 패키지 취약점이나 보안 검사도 추가할 수 있습니다.

다만 CI가 모든 문제를 알아서 찾아 주는 것은 아니고,

CI는 팀이 미리 정한 기준을 빠짐없이 반복해서 검사하는 도구입니다.

---

## 슬라이드 12

테스트 또한 모두 같은 범위를 검사하는 것은 아닌데요.

피라미드를 보시면 제일 아래에 있는 단위 테스트는 함수나 컴포넌트처럼 작은 범위를 빠르게 확인하고, 통합 테스트는 서버와 데이터베이스처럼 여러 요소가 함께 정상적으로 동작하는지 검사합니다.

그리고 E2E 테스트는 사용자가 로그인 버튼을 누르고 메인 화면에 도착하는 것처럼 전체 사용자 흐름을 확인합니다.

위로 갈수록 실제 상황과 비슷하지만 실행 시간이 길고 관리 비용도 커집니다.

따라서 하나만 사용하는 것이 아니라 목적에 맞게 적절히 조합해서 사용해야 합니다.

---

## 슬라이드 13

파이프라인을 사용하다 보면 빨간색 실패 표시를 보게 될텐데요.

보통 실패라고 하면 좋지 않은 결과처럼 느껴지지만, CI 실패는 반드시 나쁜 것만은 아닙니다.

왜냐하면 사용자에게 배포된 뒤가 아니라 배포 전에 문제를 발견했다는 뜻이기 때문입니다.

중요한 것은 실패를 완전히 없애는 것이 아니라, 어느 단계에서 왜 실패했는지를 빠르게 확인하고 수정할 수 있는가입니다.

좋은 파이프라인은 실패 원인을 이해하기 쉽게 보여줘야 합니다.

---

## 슬라이드 14

이제 검증한 결과물이 어떻게 전달되는지 살펴보겠습니다.

Artifact라는 용어가 조금 낯설 수 있는데, 쉽게 말하면 배포 가능한 결과물입니다.

소스 코드를 빌드하면 프론트엔드의 dist 폴더, 백엔드의 JAR 파일, Docker Image 같은 형태가 만들어집니다.

CI는 이 Artifact를 만들고 검증하며, CD는 검증이 끝난 같은 Artifact를 원하는 환경으로 전달합니다.

---

## 슬라이드 15

그렇다면 스테이징과 운영 환경에서 각각 다시 빌드하면 왜 안 되는지 알아보겠습니다.

같은 코드라도 빌드 시점의 패키지 버전이나 실행 환경 차이로 서로 다른 결과물이 만들어질 수 있습니다.

스테이징에서 검증한 것은 Artifact A인데 운영에서는 새로 만든 Artifact B를 배포한다면, 검증한 것과 다른 결과물을 사용자에게 전달하게 됩니다.

그래서 한 번 빌드하고 검증한 동일한 Artifact를 여러 환경에 배포하게 되는데요. 

이를 Build Once, Deploy Many원칙이라고 합니다.

---

## 슬라이드 16

이제 이 모든 결과물이 곧바로 실제 사용자에게 공개되는 것은 아닙니다.

개발 환경에서는 기능을 빠르게 확인하고, 스테이징에서는 운영과 비슷한 조건으로 QA를 진행합니다.

그 검증을 통과한 뒤 운영 환경에 배포를 하게 됩니다.

중요한 점은 환경마다 완전히 다른 코드를 사용하는 것이 아니라는 것입니다.

코드와 Artifact는 가능하면 동일하게 유지하고, API 주소나 실행 모드 같은 환경별 설정만 분리합니다.

---

## 슬라이드 17

그러면 환경마다 달라지는 설정은 어떻게 관리할까요?

API 주소나 실행 모드 같은 일반적인 설정은 환경 변수로 관리할 수 있습니다.

반면 데이터베이스 비밀번호, Access Token, API Key처럼 공개되면 안 되는 값은 Secret 저장소에 보관합니다.

이 때 Secret은 코드에 직접 작성하지 않고, 파이프라인이 실행되는 동안 필요한 위치에만 전달합니다.

또한 코드에 없더라도 실행 로그에 값이 출력되면 노출될 수 있으므로, 저장소뿐 아니라 로그에서도 보이지 않도록 관리해야 합니다.

---

## 슬라이드 18

이제 Continuous Delivery와 Continuous Deployment의 차이를 보겠습니다.

두 방식 모두 테스트, 빌드, 스테이징 배포까지는 자동화할 수 있는데요.

Continuous Delivery는 운영 배포 직전까지 준비한 뒤 사람이 마지막으로 승인합니다.

그러나 Continuous Deployment는 모든 검사와 조건을 통과하면 운영 환경까지 자동으로 배포합니다.

즉, 차이는 자동화의 유무가 아니라 마지막 운영 배포를 누가 결정하는가입니다

---

## 슬라이드 19

지금까지 배운 내용을 하나의 흐름으로 연결해 보겠습니다.

먼저 Pull Request가 생성되면 CI가 실행되고, Lint, Test, Build를 통해 코드를 검증합니다.

모든 검사를 통과하게 되면 Artifact가 만들어지고, 같은 Artifact가 스테이징 환경으로 전달되어 QA를 거칩니다.

이후 사람의 승인이나 정해진 조건을 만족하면 운영 환경에 배포되고. 어느 단계에서든 실패하면 이후 단계는 진행되지 않습니다.

---

## 슬라이드 20

마지막으로 오늘 내용을 정리하겠습니다.

오늘 설명한 내용은 단순히 하나의 CI/CD 도구 사용법을 익히기 위한 게 아니였습니다.

현재 프로젝트에서 Pull Request를 만들고, 자동 테스트가 실행되고, 결과물이 배포되는 모습을 직접 경험하고 계실 텐데요.

그때 각각의 작업을 따로 보기보다 오늘 배운 전체 흐름을 떠올려 보시면 좋을 것 같습니다.

결국 CI/CD를 한 마디로 정의하면 CI로 **코**드를 검증하고, CD로 검증한 동일한 결과물을 단계적으로 전달하는 과정입니다.

그리고 자동화의 목적은 사람을 없애는 것이 아니라, 반복 작업에서 발생하는 실수를 줄이고 사람이 중요한 판단에 집중하도록 돕는 것이라고 생각하시면 좋을 것 같습니다.

이상으로 발표를 마치겠습니다. 감사합니다.
